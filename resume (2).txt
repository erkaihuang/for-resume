## 一、项目是什么

这是一个基于 **Hypium/DeviceTest 自动化测试框架** 的 **Connectivity（无线连接）综合测试项目**，用于对智能终端设备（手机/平板等）进行**多协议、多场景的自动化连接能力测试**。

### 核心技术栈

| 层面 | 技术 |
|------|------|
| 测试框架 | Hypium / DeviceTest（自研 Python 自动化测试框架） |
| 设备控制 | ADB（Android）、HDC（OpenHarmony）、串口、TCP/IP 远程控 |
| 编程语言 | Python 3 |
| 配置管理 | XML 配置文件驱动 |
| 报告系统 | HTML 报告 + 日志收集 + BugReport 自动抓取 |
| CI/集成 | MQ 消息队列上报、TICC 服务器对接 |

### 测试覆盖的无线协议（6大模块）

1. **1_Atomic_Ability** — 原子能力测试：BLE（蓝牙低功耗）、BR（蓝牙经典）、SLE（星闪近场通信）
2. **2_BGLE** — BT_BLE 共存、GLE（星闪增强）测试
3. **4_GNSS** — 卫星定位/GPS 测试
4. **5_WIFI** — WiFi 功能与性能测试
5. **7_Infrared** — 红外遥控测试
6. **8_Coex** — 多协议共存/干扰测试（COEX_FUNCTION + COEX_PERFORM_CIDA）

### 硬件设备生态

通过 `user_config_001.xml` 可以看到，测试环境涉及 **10+ 种硬件设备**：

- **DUT 被测机**：OpenHarmony 手机（通过 HDC 连接）
- **M7600**：射频综测仪（安立）
- **TurnTableControl**：电动转台（360°旋转，用于 OTA 角度测试）
- **AntiInterferenceSceneControl**：抗干扰场景控制器
- **BizAP1**：WiFi AP（接入点），支持 2.4G/5G、EAP 认证
- **蓝牙设备**：Jabra 耳机、华为 FreeBuds Pro 3/5、罗技鼠标、华为鼠标 CD26
- **星闪设备**：SLE Mouse
- **BLE 设备**：荣耀手环

### 架构亮点

- **`devicetest` 框架**：自研的完整测试运行器，包含 TestRunner → TestCase → TestMethod 三层结构，支持 setup/teardown、结果上报、日志收集、截图、BugReport 自动抓取
- **`aw` 目录**：20+ 种硬件设备的驱动适配层（AW = AutoWare），每个设备一套独立的控制脚本
- **`controllers`**：设备控制器抽象层（Android、ADB、UIAutomator、Monkey 等）
- **`agent`**：CI 对接层（MQ 消息队列、TICC 服务器上报）
- **主测试流**：`main_test.py` 通过 `xdevice` 框架按角度（0°~300°，30°步进）批量执行 OTA 方向性测试

kpi-db-sync — 三机 KPI 测值统一数据库汇聚系统

跨主机测试数据治理与增量同步 · ip177 / ip176 / ip39 → 177 中心库

技术栈：Python · SQLite · openpyxl · XML/JSON 解析 · Windows 网络共享（d$）· argparse CLI

项目背景
KPI 测试分散在三台测试机上，历史数据只以"平铺副本"形式归档，副本不全（如 177 平铺 140 期 vs 原始 145 期），无法支撑统一查询与后续上服务器。目标是把三台机器的原始测值汇聚到 177 上的单一 SQLite 库 D:\KPI数据库\kpi_test_result.db，实现可迁移、可增量、可导出的数据底座。

核心工作

异构数据源归一：三机数据形态完全不同，分别设计采集器——
ip177：递归扫描 reports 根下所有 test_result.log（嵌套 details 树 142 个 + 散落单 case 报告 4 个），散落报告通过 summary_report.xml 的 testsuite name 反推 case 归属，多 case 无法归属的自动跳过并告警；
ip176：无原生 log，改从 iperfPressLogCOEX.xlsx（55 个 task）抽取，复用 build_json_for_case 归一成同构测值；
ip39：通过 d$ 共享访问 task_xxx\block_xxx\iperfPressLogCOEX.xlsx（26 个），日期优先取 block 级 summary_report.xml start_time，缺失时用 iperf 文件名中的日期兜底。
多格式协议解析：统一解析三类日志形态——simple 单值、B002 up/down JSON（含 up_2 单键退化形态）、B003 TX/RX details JSON，并据此还原上行/下行方向。
幂等增量同步：以唯一索引 (host, case_id, direction, test_date, seq) 为去重键，--update 只插入新行，重复执行新增 0 行（3103 行库重跑验证：新增 0 / 跳过 3103）；支持 --host 按机器单点更新。
序列号分配：同一天同一用例多轮测试按 source 排序稳定编号 seq（1=第一遍），完整保留重复测值不丢失。
维度回填：新增 biz（蓝牙业务）与 band（带宽/包型）两列，从各机 xlsx 键列推导——biz 取 keys[0]，band 为去掉业务/用例编号/level/T-RX 后的剩余键（如 20M、20M / 128字节、GC/GO）；B003 家族仅有上行行时，下行行按 case 级兜底复用。
旧库平滑迁移：--migrate 逻辑自动 ALTER TABLE 补列并从原始 xlsx 回填，无需重建库。
Excel 导出：--export 输出全量 xlsx，列序按业务要求定制（蓝牙业务 | 带宽/包型 | 用例编号 | sheet | 方向 | 测试日期 | seq | value | host | source），host 置末、不暴露内部 fmt 字段。
CLI 工程化：--list 干跑预览、--db 自定义库路径、--update / --export 子模式，便于迁移与测试。
成果

首次全量建库 4248 行：ip177 231 行 / 71 case、ip176 2872 行 / 162 case、ip39 1145 行 / 166 case。
与平铺备份交叉校验：平铺缺 5 期（177 的 2026-10-29 seq2-6）已由原始源补全，平铺有而库无 = 0，零遗漏。
单文件库约 1.1 MB，目标服务器确定后直接复制即可迁移，无需重建。
关键问题定位

发现 ip39 曾因 IP 配错（145.39）导致采到 0 行，修正为 100.103.146.39 后补回 1145 行；
修复 build_json_for_case 单方向退化丢方向的缺陷（曾致 176 的 162 case 掉到 132），改从 xlsx 原始 direction 字段取；
规避 SQLite 保留字 case，列名统一为 case_id。


下面以面试官视角，围绕 kpi-db-sync（三机 KPI 测值统一数据库） 这个项目提问。每题给出「考察点 → 参考答案 → 可能的追问」。

一、项目背景与动机
Q1：先简单介绍一下这个项目，你解决的核心问题是什么？

考察点：能否一句话讲清价值，而不是堆技术名词。

参考答案：
三台 KPI 测试机（ip177 / ip176 / ip39）各自产出测试报告，历史数据只以"平铺归档"的形式存在 D:\KPI报告归档\test_result_logs。我接手时发现这个平铺副本本身就不全——比如 177 平铺只有 140 期，而原始报告有 145 期。所以我要做的不是"把归档文件再拷一遍"，而是从三台机器的原始报告重新解析测值，汇聚到 177 上的一个 SQLite 单文件库里，让数据可统一查询、可增量更新、后续能整体迁到服务器。

核心难点不在"写库"，而在三台机器的数据形态完全不同，必须分别设计采集器再归一到同一张表。

追问预案：为什么用 SQLite 而不是 MySQL？
→ 目标服务器还没定，单文件 .db 约 1.1 MB，直接复制即可迁移，零部署成本；等服务器确定后再迁移，届时只需改 DB_FILE 或 --db 参数。用重数据库反而增加前期负担。

Q2：为什么不用现成的平铺归档，非要重新扫原始报告？

考察点：是否做过数据源评估，而不是盲目实现。

参考答案：
我先做了交叉校验，结论是平铺副本确实不全。典型例子是 177 的 COEX_002_B002_03_HiWMob_5_X_160_020 在 2026-10-29 的第 2~6 遍散落在原始目录里，平铺归档只留了一部分。所以我定了一条验收标准：平铺有而数据库没有的必须为 0，反向允许数据库比平铺多。最终结果就是平铺缺的 5 期由原始源补全，零遗漏。

同时我保留了平铺目录只作备份、不写入，避免把"备份"和"数据源"两个角色混在一起。

二、架构与数据处理设计
Q3：三台机器数据源差异这么大，你是怎么统一建模的？

考察点：抽象能力，能否把异构输入收敛到统一 schema。

参考答案：
统一到一张 test_result 表，业务字段是 host / case_id / sheet / direction / test_date / seq / value，加 fmt / source 做溯源，加 biz / band 做维度。

三台机器的采集策略分别定制：

机器	原始源	处理方式
ip177	reports 根下所有 test_result.log（嵌套 details 树 142 个 + 散落 4 个）	直接解析日志
ip176	无原生 log，只有 iperfPressLogCOEX.xlsx（55 个 task）	从 xlsx 抽取，复用 build_json_for_case 归一成同构测值
ip39	通过 d$ 共享访问 task_xxx\block_xxx\iperfPressLogCOEX.xlsx（26 个）	同 176，但日期取 block 级 summary_report.xml
关键设计：176 和 39 共用同一个 _collect_from_xlsx 函数，因为它们都是"task / task+block"目录结构且都没有可用原生 log——抽象的依据是数据形态，不是机器编号。

追问预案：那 177 为什么不也走 xlsx？
→ 177 有原生 test_result.log，日志才是原始测值的一手来源；xlsx 是二次汇总产物，用它反而可能引入中间环节的丢失。

Q4：日志格式有几种？你怎么保证解析不漏？

考察点：对数据契约的掌握程度。

参考答案：
三类格式，对应三种解析分支：

simple：日志内容就是一个浮点数。方向靠 case 后缀判断，_T=上行、_R=下行。
B002 up/down JSON：完整形态有 up_1/up_2/UP/down_1/down_2/DOWN，取值优先级是 UP > up_1 > up_2；还支持只有 up_2 单键的退化形态（散落的单 case 报告就是这种）。
B003 TX/RX JSON：从 details.iperf_result_TX / iperf_result_RX 取，TX=上行、RX=下行。
这里踩过一个真实的坑：176 的 B001_STAUT、B006 这类单方向 case，走 build_json_for_case 后会退化成 simple，方向信息就丢了。如果还按 case 后缀猜方向，这些 case 会被整批跳过——当时 case 数从 162 掉到了 132。修法是 collect_ip176 不再依赖退化后的结果，而是直接读 xlsx 原始行的 direction 字段。

追问预案：怎么发现掉的？
→ 建库后做了 case 数对账，和平铺/原始目录的 case 清单比对，发现对不上才定位到解析分支。

Q5：怎么保证重复跑不产生重复数据？

考察点：幂等性设计，这是数据同步的核心考点。

参考答案：
用业务唯一键做去重：(host, case_id, direction, test_date, seq)，建 UNIQUE INDEX，写入用 INSERT OR IGNORE，同时内存里维护一份已存在键集合先做跳过。

全量模式：删库重建。
增量模式 --update：只插新键，已存在的跳过。
幂等性验证：3103 行的库重跑一次 → 新增 0 / 跳过 3103。另外做过"删 1 行再 update"的验证，能精确补回 1 行，说明既不会重复也不会漏补。

追问预案：为什么唯一键里要放 seq？
→ 因为同一天同一用例会跑多遍，测值不同但都是真实数据，不能互相覆盖。seq 表示"当天第几遍"，按 source 排序稳定分配，1=第一遍。如果唯一键不带 seq，多轮测试就会被压成一条，等于丢数据。

Q6：biz（蓝牙业务）和 band（带宽/包型）这两列是怎么来的？为什么不直接从日志里取？

考察点：维度建模能力，以及是否理解"测值"和"维度"来源不同。

参考答案：
这两列不在日志里，只在 xlsx 的键列里。所以是从各机 xlsx 反推：

biz = 键列 keys[0]，比如 BT打开 / BT关联 / BT音乐 / BLE L2HC320音乐。
band = 键列去掉 蓝牙业务 / 用例编号 / level / T-RX 之后剩下的部分，比如 20M、20M / 128字节、GC/GO。
一个特殊处理：B003 家族的 xlsx 只有上行行，但数据库按 TX/RX 拆出了上下行。下行行取不到对应方向的 band，我用 case 级兜底（cband.get((case, direc)) or cband.get((case, ""))），保证下行行也有带宽信息。

遗留空值我也清楚：177 的 104 行 B002 散落死行（sheet 空、value 恒为 0.0，本身无真实数据）+ 176 的 192 行 B013_MCM（该 sheet 本来就没有带宽列）。这些不是 bug，是数据源客观缺失。

三、故障排查
Q7：讲一个你排查时间最长的问题。

考察点：排查方法论，比"修好了"更重要的是"怎么找到的"。

参考答案：
ip39 采到 0 行。现象是建库只有 3103 行，ip39 一条都没有。

排查路径：

先确认代码分支有没有被调用 → 有，collect_ip39 正常执行；
再确认路径可达 → 报"report 根不可达"；
回到配置查 IP，发现配的是 100.103.145.39，实际是 100.103.146.39——第三段写错了。
修正后立刻补回 1145 行 / 166 case。

复盘：这类问题的教训是——采集器返回 0 行时必须显式告警，而不是静默通过。所以我在 _collect_from_xlsx 里加了"根不可达"的打印，让"0 行"能被区分成"真没数据"还是"路径错"。

追问预案：如果机器真的没数据呢？
→ 那就应该在 meta 表里记 0，而不是报错。区别在于路径可达但无文件 vs 路径不可达，这两种要打印不同信息。

Q8：还有哪些"看起来能跑但结果不对"的坑？

考察点：是否真的踩过细节，而不是只会跑通 happy path。

参考答案：
两个：

SQLite 保留字：字段本来想叫 case，建表直接报 near "case": syntax error，改成 case_id。
散落 block 根日志无法归属：block_4142073814876946449_1 里内容是 B003 的 TX/RX 975.43，但这个目录下没有能唯一确定 case 的 summary_report.xml。我的处理是宁可跳过并告警，也不猜——猜错会污染数据，跳过至少可追溯。最终只跳了 1 个。
追问预案：为什么不人工补进去？
→ 可以，但要有明确的归属依据。在拿不到依据前，静默补数据是更危险的选择。

四、工程化与反思
Q9：这个脚本的接口是怎么设计的？

考察点：是否考虑过使用者（包括未来的自己）。

参考答案：
CLI 分了几个正交的模式：

纯文本
python build_kpi_db.py                    # 全量重建
python build_kpi_db.py --list             # 干跑，只列计划不写库
python build_kpi_db.py --update           # 增量，幂等
python build_kpi_db.py --update --host ip176   # 单机更新
python build_kpi_db.py --db <path>        # 自定义库路径（迁移/测试）
python build_kpi_db.py --export           # 导出全量 Excel
两个设计意图：

--list 干跑：在真正写库前先看扫描计划，避免"跑完才发现扫错目录"。
--db 可指定：迁移到服务器或做测试时不用改代码。
--export 的列序是业务方明确要求的：蓝牙业务 | 带宽/包型 | 用例编号 | sheet | 方向 | 测试日期 | seq | value | host | source——host 放最后、不暴露内部 fmt 字段。同时导出前会自动执行 biz/band 迁移回填，避免旧库导出来是空列。

Q10：如果让你重做一遍，你会改什么？

考察点：反思能力，这是区分"完成"和"做好"的分水岭。

参考答案：
三点：

配置外置：IP 和路径现在硬编码在 k.host_to_path 里，145.39 那个错误本质上是配置问题。应该抽成配置文件或环境变量，并在启动时做一次可达性预检。
采集结果要自证：现在靠 print 输出行数，人肉判断。更好的做法是每次采集产出结构化报告（源目录数 / 文件数 / 解析成功数 / 跳过数及原因），直接落 meta 表，让"数据少了"变成可查询的事实而不是需要重跑才知道。
跳过项要可回放：目前无法归属的散落日志只是打印出来。应该落一张 skipped 表，记录路径和跳过原因，后续补充归属规则后可以定向重放，而不是全量重扫。
五、压力提问（面试官常用来压节奏）
Q11：这个项目听起来就是写了个 ETL 脚本，技术含量在哪？

参考答法（不辩解，讲清楚难点分布）：
"如果只看代码行数，确实是一个 ETL。但它的难点不在 ETL 框架，而在数据契约的不统一——三台机器三种源、三种日志格式、加上单方向退化丢方向这类隐蔽 bug，任何一个处理错都会静默丢数据。我做的核心工作是先建立可验证的正确性标准（case 数对账、平铺与库的双向比对、幂等重跑验证），再在这个标准下逐个消除差异。最终 4248 行、零遗漏、重跑新增 0，这些数字是可以复核的。"

Q12：数据量再大 100 倍怎么办？

参考答法：
"当前 4248 行、1.1 MB，SQLite 完全够。放大 100 倍到 40 万行也还是 SQLite 的舒适区。真正的瓶颈会出现在扫描侧——现在每次 --update 都全量扫三台机器的原始目录再内存去重。到那个量级我会改成：① 按 test_date 增量窗口扫描，只扫最近 N 天；② 用源文件 mtime/大小做指纹，未变更的目录直接跳过；③ 去重从内存集合改成依赖唯一索引 + INSERT OR IGNORE，避免把全表键读进内存。"
